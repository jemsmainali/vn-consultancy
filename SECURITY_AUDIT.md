# Security audit: VN Consultancy / VN Group

**Scope:** Phase A read-only source and configuration review on 22 October 2026. No application code was changed. Review covered the FastAPI routes, dependencies, models, schemas, auth/security helpers, upload handling, React auth/API/forms, dependency manifests, environment examples, Git status/history, and available deployment/config files. No Dockerfile, compose file, reverse-proxy config, or hosting deployment manifest was present.

## Secret scan notice

A development-style PostgreSQL URL with a password field is committed in `.env.example:11`. It points to localhost and looks like sample configuration, not evidence of a production database credential. No committed `.env`, SQL dump, or database backup was found in the checked Git history. An ignored local `.env` exists and is not tracked. Its values were not included in this report. A search command during this review printed its `SECRET_KEY` line in tool output; treat that local key as exposed and rotate it if it is active. Rotate other active credentials in that local file if they were included in the same output or have otherwise been shared.

| SEC-01 | High | Secret handling / JWT | `.env:4` (ignored local file; value omitted) | The local `SECRET_KEY` line was printed during the audit search. This key signs JWTs and also keys OTP hashes. | Anyone who can access that output and the running service could forge login tokens or undermine OTP verification if the key is active. | Rotate the active key immediately and invalidate sessions/OTPs signed with it. | SEC-02 | High | JWT configuration | `app/core/config.py:9-12`; `.env.example:4` | There is no startup validation for secret entropy/length or production algorithm configuration. The example secret is deliberately a human-readable placeholder, and the application accepts any configured `SECRET_KEY`. | If a deployment copies the example unchanged or uses a short/predictable key, an attacker who guesses it can forge JWTs and impersonate accounts. | Fail startup in production unless the key is generated with at least 32 random bytes; pin accepted JWT algorithms in code and reject unsafe settings. ## What is already good

- Privileged roles require configured invite codes and remain pending until an existing staff user approves them.
- Passwords use bcrypt. Access and refresh JWTs have expiry claims and distinct token types; decoding restricts to the configured algorithm.
- Browser tokens are held in `HttpOnly`, `SameSite=Lax` cookies rather than local storage. Refresh checks current user active, verified, and approval state.
- Document list and ID routes check ownership or staff role; message threads are limited to the two participants.
- Uploads use server-side magic-byte detection, size settings, random filenames, basename-safe paths, and are stored outside a public static mount.
- Bank account numbers are encrypted at rest in the application data model and are omitted from user response schemas.
- Validation error handling removes submitted values, and reset responses avoid account enumeration.
- Rate limits cover login, registration, OTP/reset routes, and public enquiry submission.
- ORM query construction avoids user-interpolated SQL. Frontend output uses normal React text rendering without raw HTML insertion.
- CORS is configured from an explicit origin list; API responses set several useful security headers.
- `npm audit` found zero vulnerabilities in the frontend lockfile at review time.

## Suggested fix order

1. Rotate the local key exposed in the audit output (SEC-01); remove any exposed value from shared logs/transcripts where possible.
2. Enforce production JWT secret strength/algorithm and secure-cookie configuration at startup (SEC-02, SEC-05); replace the committed sample DB credential (SEC-12).
3. Add bounded upload streaming and server/proxy request limits (SEC-03); switch document downloads to attachment (SEC-06).
4. Add token revocation and CSRF protections for cookie-authenticated sessions (SEC-07, SEC-08).
5. Apply a tested CSP and Permissions-Policy at the frontend host; disable production OpenAPI if not required (SEC-04, SEC-11).
6. Reduce PII returned by staff actions, normalize signup duplicate responses, and tighten request field limits (SEC-09, SEC-10, SEC-13).
7. Validate message/document association (SEC-14), then run `pip-audit` and Bandit in the project's actual Python environment and resolve verified findings (SEC-15).

## Phase B note: token storage migration

Do not migrate token storage to cookies in a future fix pass: the frontend already uses `HttpOnly` cookies. If deployment topology or browser requirements change, retain cookie storage and document any cookie attribute or CSRF changes before rollout.
